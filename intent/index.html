the effect of running the intent layer

A duplicate of an irreversible action isn't caught.
It's impossible — refused at the dispatch edge, by construction.

The kernel is domain-agnostic: any irreversible action is authorized only by a reproducible, measured demonstration that it meets declared criteria. The gate is the sole emitter of a single durable ACHIEVED record, and downstream acts only on that record — so no record ⟹ the action never happened. Worked example throughout: a treasury payment, action class 1.

without

At-most-once is an assertion: dedup lives in each adapter's retry logic, audited after the fact. A retried near-duplicate can execute twice before anyone reads the log.

with the gate

The idempotency key is a declared, first-class gate criterion — required, and reserved at the dispatch edge. Same key, one changed field ⟹ FAILED_AT_DISPATCH. At-most-once holds by construction, whatever the action is.

the authorization kernel · reference implementation: treasury-intent-controller

Nothing moves until the gate says so —
one durable ACHIEVED record, or nothing at all.

A deterministic Go gate decides whether an irreversible action is authorized — the reference implementation gates treasury payments, but the kernel reads no artifacts and knows no domain: criteria, thresholds, and the idempotency key all arrive as declared params. Scoring is tri-state and fail-closed: any Fail or Unevaluable denies, and unevaluable never collapses into a pass. Volatile facts — balance, reachability — are re-checked at the dispatch edge by the same authority, immediately before authorizing. Every run replays byte-identically from a logical-clock event log.

How it works

Four moves, seven states, two terminal failures — all of them safe.

Every intent walks DECLARED → RESOLVING → ACTIVE → VERIFYING toward exactly one terminal state. Both failure states carry the same guarantee: no ACHIEVED record exists, so no consumer ever settles.

01 · declare→

Key required

Criteria, thresholds, and the idempotency key arrive as params. An absent key is unevaluable — the intent fails closed before anything runs.

02 · verify→

Score tri-state

Every declared criterion scores Pass, Fail, or Unevaluable. Any Fail or Unevaluable denies authorization — unevaluable never collapses into a pass.

03 · re-check→

The dispatch edge

Volatile facts are re-verified by the same authority immediately before authorizing, and the declared key is reserved. A drifted fact or a key collision ⟹ FAILED_AT_DISPATCH.

04 · emit■

One durable record

The gate appends the single ACHIEVED record — fsynced to the durable feed before success — and stops. Settlement belongs to whoever observes it.

Scope — emit-and-observe. The gate's job ends at the durable ACHIEVED record. It settles nothing and never calls out; a settlement consumer pulls the feed by cursor and recomputes. A crash on either side loses nothing.

Invariants

Six properties, enforced by construction and pinned by tests.

None of these is a convention the code tries to follow. Each is a structural property — violating it means failing an acceptance test, not missing a guideline.

01Sole emitter

The gate alone emits the single ACHIEVED record, fsynced to the durable feed before success is reported. Consumers act only after observing it.

02Tri-state, fail-closed

Criteria score Pass / Fail / Unevaluable. Any Fail or Unevaluable ⟹ not authorized. Absence of valid proof is a denial, never a default-pass.

03Stable vs volatile

Stable criteria are scored once, at declaration. Volatile facts are scored at declaration and re-verified at the dispatch edge by the same authority, immediately before authorizing.

04Idempotency by construction

The key is required and reserved at the dispatch edge. A near-duplicate — same key, different intent hash — collides and is refused. At-most-once holds on the settlement log structurally.

05Determinism & replay

Per-intent logical clock, IDs derived from the episode seed, no wallclock. Replay drives a recompute, not a re-read — and reproduces the trajectory byte-identically.

06Durability

The event feed and the key reservations survive process restart over the same TIC_DATA_DIR — kill/restart proven: byte-identical events, same-key re-dispatch still refused, cursor gapless.

The loop around the gate

Not a pipeline — a loop, closed over three hashes.

At first sight this reads left to right. It isn't: the policy is signed upstream, re-verified by the gate's scorer at authorization time, and quoted back out in every settlement — rule_artifact_hash · intent_spec_hash · trajectory_hash. Every settlement joins the runtime trace to the exact signed policy it was authorized under. This is the treasury instantiation of a domain-agnostic pattern: any consequential action class can sit behind the same gate with a different declared spec.

policy plane · atlas→

IntentSpec — the signed policy

What authorizes an action — including what counts as a duplicate — is a signed, expert-attested, registry-governed artifact, published by content hash. Not adapter-local config.

this plane · the gate→

Authorization

Before any criterion is scored, the resolver re-verifies the pinned artifact — verify_artifact folded per hash; absent, rejected, or hash-mismatched ⟹ fail closed. Then tri-state scoring, the dispatch edge, one durable record.

settlement plane · compass⟲

Settlement — and the loop closes

Pulls GET /v2/events?since=cursor and recomputes from observed ACHIEVED records only. Each settlement carries the full trace record — pointing back to the signed policy that started the loop.

Why this shape

Authority is never shared — and provenance is never lost. The agent may propose; only the gate authorizes; only an observer settles. Every hand-off crosses a durable, replayable record, and the record names the signed policy by hash — so any settlement can be audited back to the exact criteria, thresholds, and duplicate-definition it ran under, and any duplicate or drifted intent reads unambiguously: the action never happened.

Built & verified what the claims above rest on›
  • The full loop ran green, live (2026-07-12): COMPASS declare → Go gate → wheel-verified scorer (a real verify_artifact of the golden signed IntentSpec) → ACHIEVED in the durable feed → cursor reconcile → settlements carrying the full trace record.
  • The negatives were probed live, not assumed: an unknown spec hash ⟹ FAILED unevaluable; a cursor-rewind restatement re-observed the feed and left the ledger byte-identical (duplicates counted, zero applied); a real scorer kill made the next declaration FAIL with zero new settlements. Outage means delay — never loss, never invention.
  • Slice 1 + the durability refactor + the live scoring seam are built and verified: the gate, the fsync-per-append durable feed with a gapless global cursor, and the Python criterion scorer answering POST /ml/evaluate — verified two-process, with a real service kill.
  • Zero-config refuses everything: with no scorer configured, every intent is unevaluable and therefore denied. The default posture of the system is "no".
  • The IntentSpec artifact type is merged upstream (ATLAS, ADR-0021/0022) — it flows through the same compile · sign · attest · publish lifecycle as rule artifacts, and is consumed strictly by hash.
Honesty boundaries 3 stated›
  • The wheel-backed artifact reader inside the scorer is Linux/CI-only for now — its test lane skips visibly rather than silently until it lands everywhere.
  • The consumer's criteria/threshold config is app config bound to the pinned spec hash, not yet extracted from the IntentSpec payload itself — recorded parity debt, not a hidden gap.
  • No production claim. This is a working authorization plane with proven invariants, not a deployed payment system; the settlement consumer's durable ledger adapter for serverless hosting is planned, and the cron makes no durability claim until it exists.
